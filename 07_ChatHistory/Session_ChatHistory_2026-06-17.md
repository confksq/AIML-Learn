That's the **context window usage indicator** — it's different from credits.

**What it means:**
- Claude's model can only "see" a certain amount of text at once (the context window)

- You have to start a new session at that point

- Claude Code has **auto-compression** that kicks in before it fills up — it summarizes older parts of the conversation to make room (that's what happened in this session — the early messages got compressed into the summary you saw)
- Most sessions compress successfully and never hit 100%
- It tends to happen in very long sessions where a lot of large files were read

**Credits vs Context — quick distinction:**

| | Credits | Context (%) |
|---|---|---|
| What it is | Billing (API cost) | Model memory capacity |

| Hits limit | Session keeps going, you get billed | Session stops completely |

## Claude

**Yes, it does automatically remove old documents.** Here's exactly how it works, confirmed from the code:

**Every sync run (daily at 09:00 or on startup):**

1. Calculates `retentionCutoff = today - 24 months`
   - e.g. on 06/17/2026 → cutoff = 06/17/2024

2. Pulls all SharePoint items. For each document:
   - If `scannedDate < cutoff` → **skipped** (not added to the "keep" list)
   - If `scannedDate >= cutoff` → uploaded to index and added to the keep list

3. After all docs are processed, calls `DeleteMissingDocumentsAsync(activeDocumentIds)`:
   - Gets every document ID currently in the index
   - Any ID **not** in the keep list → **deleted from the index**

So your scenario is exactly right:

| Date | Cutoff | What happens |
|---|---|---|
| 06/16/2026 | 06/16/2024 | Docs scanned on 06/16/2024 still included (≥ cutoff) |
| 06/17/2026 | 06/17/2024 | Docs scanned on 06/16/2024 are now < cutoff → removed |

The index is essentially a **rolling 24-month window** — it self-cleans every sync run. No manual intervention needed.

The Azure AI Search service (`srch-jma-prod-indexer`) **never talks to SharePoint directly**. It's a passive store. Here's the actual flow from the code:

```
App Service (app-jma-prod-docmgmt-aisearch-api)
│
├── EnterpriseSearch.Sync (background Worker)
│     │
│     ├── GraphReaderService → calls SharePoint via Microsoft Graph
│     │   using JMA-Sharepoint Search-Indexer-PRD (client credentials)
│     │
│     └── IndexWriterService → writes results into AI Search index
│         using App Service Managed Identity (Search RBAC roles)
│
└── EnterpriseSearch.Api (web API)
      ├── SearchService → queries AI Search index (MI)
      └── GraphService → downloads file from SharePoint (same app reg)
```

So the **App Service itself is the bridge** — it pulls from SharePoint and pushes into AI Search. Azure AI Search has no connection to SharePoint at all.

This confirms everything:
- **1 M365 ticket** → `JMA-Sharepoint Search-Indexer-PRD` needs `Sites.Selected` (used by both the sync and download)
- **AI Search RBAC roles** → assigned to the App Service Managed Identity (no M365 involvement, handled by resource-run workflow)
- **Azure AI Search** → just stores and serves the index, no SharePoint communication
