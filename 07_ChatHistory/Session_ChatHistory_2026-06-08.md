## Claude

Good question. There are **two separate permission systems** at play, and `AKS_Admin` only covers one of them.

---

**1. Azure control plane** — managing Azure resources, creating role assignments
- Requires: `Microsoft.Authorization/roleAssignments/write`
- Who has it: `Owner` or `User Access Administrator` roles
- `AKS_Admin` has it? ❌ Not included

**2. Kubernetes data plane** — deploying pods, services, secrets inside the cluster
- Requires: AKS data actions (`Microsoft.ContainerService/managedClusters/*`)
- `AKS_Admin` has it? ✅ Yes (with the `secrets/read` restriction)

---

`AKS_Admin` only covers the **Kubernetes data plane** side. It lets the SP run `kubectl apply`, deploy workloads, etc. — but it has **zero ability to create or modify Azure role assignments** because that lives on the control plane side.

So when the workflow's "Grant AKS namespace deployment access" step runs `az role assignment create`, it's a control plane call — and `AKS_Admin` gives no control plane write access at all. That's why it fails regardless of what scope `AKS_Admin` is assigned at.

**In short:**
- `AKS_Admin` = can deploy *into* Kubernetes
- `Owner/UAA` = can manage *who has access* to Azure resources

The workflow was trying to do both. The platform team gave it the first but not the second — which is actually correct from a security standpoint. That's why we updated the workflow to skip the self-assignment step when `AKS_Admin` is already present.

The remaining blocker is purely the `secrets/read` restriction inside `AKS_Admin` that blocks Helm.
