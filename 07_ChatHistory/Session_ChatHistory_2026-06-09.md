## Claude

Good question. There are **two separate permission systems** at play, and `AKS_Admin` only covers one of them.

---

**1. Azure control plane** — managing Azure resources, creating role assignments
- Requires: `Microsoft.Authorization/roleAssignments/write`
- Who has it: `Owner` or `User Access Administrator` roles
- `AKS_Admin` has it? ❌ Not included

**2. Kubernetes data plane** — deploying pods, services, secrets inside the cluster
- Requires: AKS data actions (`Microsoft.ContainerService/managedClusters/*`)
- `AKS_Admin` has it? ✅ Yes (with the `secrets/read` restriction)

---

`AKS_Admin` only covers the **Kubernetes data plane** side. It lets the SP run `kubectl apply`, deploy workloads, etc. — but it has **zero ability to create or modify Azure role assignments** because that lives on the control plane side.

So when the workflow's "Grant AKS namespace deployment access" step runs `az role assignment create`, it's a control plane call — and `AKS_Admin` gives no control plane write access at all. That's why it fails regardless of what scope `AKS_Admin` is assigned at.

**In short:**
- `AKS_Admin` = can deploy *into* Kubernetes
- `Owner/UAA` = can manage *who has access* to Azure resources

The workflow was trying to do both. The platform team gave it the first but not the second — which is actually correct from a security standpoint. That's why we updated the workflow to skip the self-assignment step when `AKS_Admin` is already present.

The remaining blocker is purely the `secrets/read` restriction inside `AKS_Admin` that blocks Helm.

It is an **Azure Private DNS zone** — a special DNS namespace that Azure creates when you set up a Private Endpoint for a storage account.

Here is how it works step by step:

**Normal (public) DNS resolution:**
```
stajmadevdocmgmt.blob.core.windows.net
    → 52.239.x.x  (public Azure IP)
    → traffic goes over the internet / service endpoint
```

**With a Private Endpoint:**
```
stajmadevdocmgmt.blob.core.windows.net
    → stajmadevdocmgmt.privatelink.blob.core.windows.net  (CNAME redirect)
    → 10.245.10.106  (private IP inside your VNet)
    → traffic stays entirely on the private network
```

The `privatelink.blob.core.windows.net` DNS zone is what holds that final record `10.245.10.106`. Azure automatically creates and manages this zone when a Private Endpoint is provisioned.

**Why it affects the AKS pods:**

The zone is linked to the hub VNet. Because the AKS VNet is peered with the hub, it inherits the same DNS resolution. So when an AKS pod asks "what IP is `stajmadevdocmgmt.blob.core.windows.net`?", Azure DNS walks the chain:

```
pod asks DNS
  → Azure DNS (192.168.192.53 / CoreDNS)
    → hub-linked private DNS zone
      → returns 10.245.10.106  ← private endpoint, unreachable from AKS pods
```

**The intended design (paved road):**

For AKS workloads that use Service Endpoints, the pod should get the **public IP** back from DNS. Traffic then goes directly from the pod → Azure backbone via the service endpoint (no internet, no private endpoint needed). But that only works if the private DNS zone is **not** linked to the AKS VNet — because the private DNS zone, when linked, always wins over the public DNS answer.

In short: the private DNS zone was set up for a different workload (something that needs private network access to the same storage account), and the AKS VNet got caught in its blast radius because of the hub peering.
