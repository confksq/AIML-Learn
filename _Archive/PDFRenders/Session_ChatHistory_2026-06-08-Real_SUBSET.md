## ① Foundry Resource — High Level Overview

Think of the **Foundry Resource** as the **top-level Azure ARM resource** — the equivalent of a Resource Group's "owner" for all your AI work. Everything sits under it.

Its ARM type is `Microsoft.CognitiveServices/accounts`, created once in the Azure Portal.

It has **4 responsibilities:**

---

### 1.1 Model Deployments
This is where you pick **which AI model to use**. Three families:
- **OpenAI** — GPT-5, GPT-4o, o3/o4-mini (reasoning), DALL·E (images), Whisper (audio)
- **Microsoft** — Phi-4, Phi-3.5 (smaller, cheaper models)
- **Partner/Community** — Llama, Mistral, Cohere, Grok, DeepSeek + 10k+ Hugging Face models

Plus a **Model Router** that auto-picks the best model per call based on cost/latency/capability.

---

### 1.2 Deployment Types
**How** the model is hosted and billed:
- **Global Standard** — shared infrastructure, pay-per-token, flexible
- **PTU** — reserved capacity, predictable performance, higher cost
- **Serverless (MaaS)** — pure pay-per-token, no reservation needed
- **Managed Compute** — you control the hosting (Hub-based projects only)

---

### 1.3 Security Settings
Standard Azure security wired in:
- **Managed Identity** — no passwords, Azure handles auth
- **RBAC** — 4 roles from full control → read-only
- **Private Endpoints** — lock it to your VNet, no public internet

---

### 1.4 Connections
The Foundry Resource acts as a **broker** to external services your AI apps need — AI Search, Storage, Cosmos DB, SharePoint, Bing, Key Vault, etc. These are **pointers with auth**, not hosted copies.

---

**One-line summary:** The Foundry Resource is your AI foundation in Azure — pick your models, set how they're hosted, lock down security, and wire up the external services your agents will need.

## ① Foundry Resource — What, Why, Purpose & Impact

---

### What is it?
The **Foundry Resource** is a single top-level Azure resource (`Microsoft.CognitiveServices/accounts`) that acts as the **root container** for everything AI in Azure. You create it once in the Azure Portal or via IaC (Bicep/ARM). All your models, projects, agents, and connections live under it.

---

### Why do we need it?
Before Foundry, AI in Azure was **fragmented**:
- Azure OpenAI was one service
- Azure AI Services (Vision, Speech, Language) was another
- Azure Machine Learning was yet another
- Each had its own portal, SDK, billing, and security model

Foundry **unifies all of it** under one resource. One place to govern, one SDK to call, one billing dashboard to check.

---

### What's its purpose?
It serves 4 purposes:
1. **Model access** — deploy and serve any AI model (GPT, Phi, Llama, etc.)
2. **Deployment control** — decide HOW models are hosted (shared, reserved, serverless)
3. **Security boundary** — Managed Identity, RBAC, Private Endpoints all anchored here
4. **Connection hub** — pointer to every external service your AI apps need (Search, Storage, Cosmos, etc.)

---

### Where to use it?
Any scenario where you're building AI into an application:
- Enterprise chatbots / copilots
- Document processing pipelines
- AI agents that call APIs and search data
- Fine-tuned models for your domain
- Any app using GPT, embeddings, speech, vision

---

### If it doesn't exist — what happens today?
Without Foundry Resource, you'd have to:

| Problem | Impact |
|---|---|
| Call Azure OpenAI, AI Services, AML separately | 3 different SDKs, 3 auth flows, 3 portals |
| Manage security per service | RBAC scattered across resources |
| No unified agent runtime | Build orchestration yourself (LangChain, Semantic Kernel from scratch) |
| No central observability | Tracing spread across App Insights, AML logs, OpenAI logs |
| No model catalog | Manually find, configure, and deploy each model |

In 2025/2026, **not using Foundry means rebuilding the plumbing yourself** — it's the difference between wiring your own electrical system vs. plugging into a power outlet.

---

**Bottom line:** Foundry Resource is the **power outlet** for enterprise AI on Azure. Everything else plugs into it.

## Building an AI Agent in Azure AI Foundry — End to End

---

### Stack Overview

| Layer | Tool |
|---|---|
| IDE | Visual Studio 2022 |
| Language | C# (.NET 8) |
| SDK | `Azure.AI.Projects` (NuGet) |
| Portal | ai.azure.com |
| Deploy | Azure App Service / Container Apps |

---

### Step 1 — Set Up in Azure Portal (ai.azure.com)

```
1. Create Foundry Resource         → portal.azure.com
2. Create a Foundry Project        → ai.azure.com
3. Deploy a model (GPT-4o)         → Model Deployments tab
4. Add Connections                 → AI Search, Storage
5. Copy Project Endpoint URL       → used in code
```

---

### Step 2 — C# Console App in Visual Studio

**Install SDK:**
```bash
dotnet add package Azure.AI.Projects
dotnet add package Azure.Identity
```

**Agent Code:**
```csharp
using Azure.AI.Projects;
using Azure.Identity;

var client = new AIProjectClient(
    new Uri("https://your-project.api.azureml.ms"),
    new DefaultAzureCredential()  // uses Managed Identity — no passwords
);

var agentsClient = client.GetAgentsClient();

// Create the agent
var agent = await agentsClient.CreateAgentAsync(
    model: "gpt-4o",
    name: "DealerSupportAgent",
    instructions: "You help Toyota dealers find financing rates and policy info. Always cite your source."
);

// Create a conversation thread
var thread = await agentsClient.CreateThreadAsync();

// Send user message
await agentsClient.CreateMessageAsync(
    thread.Value.Id,
    MessageRole.User,
    "What is the 60-month rate for a 2025 Camry, credit score 720?"
);

// Run the agent
var run = await agentsClient.CreateRunAsync(thread.Value.Id, agent.Value.Id);

// Poll until done
while (run.Value.Status != RunStatus.Completed)
{
    await Task.Delay(1000);
    run = await agentsClient.GetRunAsync(thread.Value.Id, run.Value.Id);
}

// Get the response
var messages = agentsClient.GetMessagesAsync(thread.Value.Id);
await foreach (var msg in messages)
{
    if (msg.Role == MessageRole.Assistant)
        Console.WriteLine(msg.ContentItems[0].ToString());
}
```

---

### Step 3 — Add a Tool (AI Search for rate docs)

```csharp
// Wire up AI Search as a tool before creating the agent
var searchTool = new AzureAISearchToolDefinition(
    connectionId: "/subscriptions/.../connections/my-ai-search",
    indexName: "rate-policy-index"
);

var agent = await agentsClient.CreateAgentAsync(
    model: "gpt-4o",
    name: "DealerSupportAgent",
    instructions: "...",
    tools: new List<ToolDefinition> { searchTool }
);
```
Now the agent **automatically searches your documents** before answering.

---

### Step 4 — Deploy the App

```
Option A: Azure App Service
  → Publish from Visual Studio → Azure App Service
  → Assign Managed Identity to the App Service
  → App Service calls Foundry using that identity — no API keys

Option B: Azure Container Apps
  → Dockerize the app
  → azd up   (provisions + deploys everything via Bicep IaC)
```

---

### Full Picture

```
User (browser/Teams/API)
        ↓
Azure App Service  (.NET 8 app)
        ↓
Azure.AI.Projects SDK
        ↓
Foundry Project Endpoint
        ↓
Agent Runtime (GPT-4o)
    ├── AI Search tool  → searches rate docs
    ├── Function tool   → calls your pricing API
    └── Answer compiled → returned to user
```

---

```python

```

---

**Key takeaway:** You write C# like any other Azure SDK call. Foundry handles the model, the tool routing, the memory (threads), and the security. You just define the agent's behavior and wire up the tools.

## 4 Deployment Types — Simple Explanation

---

### 1. Global Standard (Shared)
```
You share Microsoft's servers with other customers
Pay per token used
No guarantee on speed during peak times
```
**Real life:** Like riding a **public bus** — cheap, works fine, but if it's rush hour it might be slow. Best for dev/test or low traffic apps.

---

### 2. Provisioned Throughput — PTU (Reserved)
```
Microsoft reserves capacity just for you
Fixed monthly cost regardless of usage
Guaranteed speed and performance
```
**Real life:** Like **leasing a private car** — you pay monthly whether you drive or not, but it's always available and fast. Best for production apps with heavy traffic.

---

### 3. Serverless / MaaS (Pay per token)
```
No setup, no reservation
Call the model, pay only for what you use
Model is from the catalog (Llama, Mistral, Cohere etc.)
```
**Real life:** Like an **Uber** — no commitment, call when needed, pay per trip. Best for partner/community models you use occasionally.

---

### 4. Managed Compute (Self-hosted on Azure)
```
Model runs on YOUR Azure ML compute (GPU VMs)
You control everything
Only available in Hub-Based projects
```
**Real life:** Like **buying your own car** — full control, higher cost, you manage maintenance. Best for custom fine-tuned models or strict data compliance requirements.

---

### Summary Table

| Type | Who runs it | Cost | Best for |
|---|---|---|---|
| Global Standard | Microsoft (shared) | Pay per token | Dev / low traffic |
| PTU | Microsoft (reserved) | Fixed monthly | Production / high traffic |
| Serverless | Microsoft (shared) | Pay per token | Partner models / occasional use |
| Managed Compute | You (Azure GPU VMs) | VM cost | Fine-tuned / compliance |

---

**90% of projects use Global Standard for dev and PTU for production.** The other two are for specific scenarios.

## ② Foundry Project (New Gen) — What, Why, Purpose & Impact

---

### What is it?
The **Foundry Project** is your **AI development workspace** — it lives inside the Foundry Resource. This is where you actually **build things**. If the Foundry Resource is the building, the Foundry Project is your office inside it where all the real work happens.

---

### Why do we need it?
The Foundry Resource alone just gives you model access. You can't build agents, run evaluations, test in a playground, or write code without a Project. It's the **working layer** on top of the resource.

---

### What's its purpose?
It has **7 capabilities** under it:

| # | Capability | What it does |
|---|---|---|
| 2.1 | Agent Service | Build and run AI agents |
| 2.2 | Playground | Test models and agents — zero code |
| 2.3 | Evaluations | Score your agent's output quality |
| 2.4 | Observability | Trace every step your agent takes |
| 2.5 | Fine-tuning | Train the model on your own data |
| 2.6 | Files & Data | Upload documents for your agent to search |
| 2.7 | Project Endpoint | The URL your C# app calls |

---

### Where to use it?
Every time you build an AI feature:
- Customer support chatbot
- Document processing agent
- Internal knowledge search
- Automated report generation

One project per application or team is the recommended pattern.

---

### If it doesn't exist — what happens today?

| Problem | Impact |
|---|---|
| No Agent Service | Build orchestration yourself from scratch using LangChain or Semantic Kernel |
| No Playground | No way to test the model without writing code first |
| No built-in Evaluations | Manually score outputs — no automation |
| No Observability | No idea what your agent did step by step |
| No Project Endpoint | No single URL for your app to call |

Without it you'd spend weeks building plumbing before writing a single line of business logic.

---

**Bottom line:** Foundry Resource = the foundation. Foundry Project = where you build. You can't do any real AI work without a Project.
