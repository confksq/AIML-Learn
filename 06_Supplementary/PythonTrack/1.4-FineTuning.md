## Concept 1 — What Is Fine-Tuning and Why Do We Need It?

### 1. Real-World Problem (Hook)

You work at a law firm. You buy access to GPT-4 — a brilliant general AI.

You ask it: *"Summarize this legal contract and flag unusual indemnity clauses."*

It gives a decent answer — but it uses casual language, misses legal nuance, and doesn't follow your firm's specific format.

**The problem:** GPT-4 was trained on everything — cooking blogs, Reddit posts, Wikipedia, code — not specifically on legal documents and your firm's style.

You need it to **behave like a specialist lawyer**, not a generalist.

That is exactly what fine-tuning solves.

---

### 2. Simple Concept Explanation

Fine-tuning means taking a pre-trained model and **continuing to train it on your specific data** so it learns your domain, style, and format.

Think of it like this:

- **Pre-trained model** = a university graduate (knows everything broadly)
- **Fine-tuning** = a 6-month internship at your firm (learns your specific way of working)
- **The graduate's general knowledge** is not erased — it is extended and specialised

The model keeps everything it learned during pre-training. You just add more training on top with your data.

---

### 3. Diagram

```
GENERAL MODEL (pre-trained)
        │
        │  knows: language, math, code, history...
        │  does NOT know: your company's tone, domain rules, output format
        │
        ▼
  ┌─────────────────────────────┐
  │   Your Fine-Tuning Data     │
  │   (instruction + response)  │
  │                             │
  │  "Summarize this contract"  │
  │  → "The agreement states..."│
  └─────────────────────────────┘
        │
        │  Model trains on your examples
        │  Weights get nudged toward your style
        │
        ▼
SPECIALISED MODEL (fine-tuned)
        │
        │  knows: everything before + your domain
        │  outputs: your format, your tone, your rules
```

---

### 4. Step-by-Step Breakdown

```
Step 1 → Start with a pre-trained model (Llama 3, Mistral, GPT etc.)

Step 2 → Prepare your training data
         Format: instruction + response pairs
         Example:
         {
           "instruction": "Summarize this contract.",
           "input": "This agreement between Party A and...",
           "output": "The contract establishes a 2-year..."
         }

Step 3 → Feed your data through the model (forward pass)
         Model makes a prediction for each response

Step 4 → Calculate loss
         How wrong was the model's prediction vs your correct response?

Step 5 → Backpropagate
         Adjust weights slightly toward your correct answers

Step 6 → Repeat for all your examples, multiple times (epochs)

Step 7 → Save the fine-tuned model weights
```

---

### 5. Code Implementation

```python
# We use a small model (GPT-2) to demonstrate the concept locally
# In production you would use Llama 3 / Mistral on a GPU

from transformers import AutoTokenizer, AutoModelForCausalLM, TrainingArguments, Trainer
from datasets import Dataset

# --- Step 1: Load base model ---
model_name = "gpt2"
tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token

model = AutoModelForCausalLM.from_pretrained(model_name)

# --- Step 2: Prepare your data ---
data = [
    {"text": "Instruction: Summarize the contract.\nResponse: The agreement is for 2 years with monthly payments."},
    {"text": "Instruction: Find the termination clause.\nResponse: Either party may terminate with 30 days written notice."},
    {"text": "Instruction: What is the payment term?\nResponse: Payment is due within 15 days of invoice receipt."},
]
dataset = Dataset.from_list(data)

# --- Step 3: Tokenize ---
def tokenize(example):
    return tokenizer(
        example["text"],
        truncation=True,
        max_length=128,
        padding="max_length"
    )

tokenized = dataset.map(tokenize)

# --- Step 4: Train ---
training_args = TrainingArguments(
    output_dir="./fine_tuned_model",
    num_train_epochs=3,            # how many times to see all data
    per_device_train_batch_size=1,
    logging_steps=1,
    save_strategy="no"
)

trainer = Trainer(
    model=model,
    args=training_args,
    train_dataset=tokenized,
)

trainer.train()
print("Fine-tuning complete.")
```

---

### 6. Output Explanation

```
Step 1/3 - Loss: 3.84  ← model is very wrong at the start
Step 2/3 - Loss: 2.11  ← getting better
Step 3/3 - Loss: 1.43  ← much more aligned with your data
```

**Loss** = how wrong the model is. As training progresses, loss decreases — the model's outputs get closer to your target responses.

After training, the model weights are permanently adjusted to favour your domain.

---

### 7. Common Mistakes

| Mistake | What Actually Happens | Fix |
|---------|----------------------|-----|
| Too little data (< 100 examples) | Model barely changes behaviour | Aim for 1,000–10,000 examples |
| Too many epochs | Model memorises training data, fails on new input (overfitting) | Use 3–5 epochs, monitor validation loss |
| Fine-tuning for knowledge updates | New facts become stale quickly as world changes | Use RAG instead for knowledge, fine-tune only for behaviour |
| Forgetting base capabilities | Model forgets how to do general tasks (catastrophic forgetting) | Use LoRA (next concept) — it preserves base weights |

## Concept 2 — LoRA (Low-Rank Adaptation)

### 1. Real-World Problem (Hook)

Fine-tuning a 7 billion parameter model sounds great — but here is the problem:

- 7B parameters × 4 bytes each = **28 GB** just to store the model
- During training you also need gradients and optimizer states = **~90 GB total**
- A top-of-the-line consumer GPU (RTX 4090) has only **24 GB**

Full fine-tuning is impossible for most people and companies.

**LoRA solves this.** It lets you fine-tune a 7B model using only **~6 GB of GPU memory** — on a single affordable GPU.

---

### 2. Simple Concept Explanation

Instead of changing ALL the model's weights (7 billion numbers), LoRA:

1. **Freezes** all original weights (they stay exactly as they are)
2. **Adds tiny extra matrices** next to certain layers
3. **Only trains those tiny matrices**

These tiny matrices are so small that training them takes a fraction of the memory and time.

At the end, you merge them back into the original weights to get your fine-tuned model.

**Analogy:**
Imagine a book (the pre-trained model). Instead of rewriting the whole book, you add **sticky notes** in the margins. The book stays the same. The sticky notes hold your new knowledge. Together, book + sticky notes = your specialised model.

---

### 3. Diagram

```
WITHOUT LoRA (Full Fine-Tuning):
┌─────────────────────────────────────┐
│   Weight Matrix W  (4096 × 4096)    │  ← 16.7 million numbers to update
│   ALL of these get updated          │
└─────────────────────────────────────┘

WITH LoRA:
┌─────────────────────────────────────┐
│   Weight Matrix W  (4096 × 4096)    │  ← FROZEN. Not touched.
└─────────────────────────────────────┘
              +
┌──────────┐     ┌──────────┐
│  A       │  ×  │  B       │   ← Only these are trained
│ 4096 × 8 │     │ 8 × 4096 │   ← rank r = 8
└──────────┘     └──────────┘
  65,536 numbers total  (0.4% of original!)

Final output = W + (A × B)
```

---

### 4. Step-by-Step Breakdown

```
Step 1 → Choose which layers to add LoRA to
         Usually the attention layers: q_proj, v_proj, k_proj, o_proj

Step 2 → Choose the rank (r)
         r = 8  →  small adapter, fast training, less expressive
         r = 64 →  larger adapter, slower, more expressive

Step 3 → Freeze all original weights
         model.requires_grad_(False)

Step 4 → Inject A and B matrices into chosen layers
         These start near zero (so they add nothing at the start)

Step 5 → Train only A and B matrices
         Original model behaviour is preserved from the start

Step 6 → At inference: output = W_frozen + (A × B)
         Or merge permanently: W_new = W + (A × B)
```

---

### 5. Code Implementation

```python
# pip install transformers peft

from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model, TaskType

# --- Step 1: Load base model ---
model_name = "gpt2"
tokenizer = AutoTokenizer.from_pretrained(model_name)
model = AutoModelForCausalLM.from_pretrained(model_name)

# --- Step 2: Check parameters BEFORE LoRA ---
total = sum(p.numel() for p in model.parameters())
print(f"Before LoRA — Total parameters: {total:,}")

# --- Step 3: Define LoRA config ---
lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=8,                        # rank — the size of the tiny matrices
    lora_alpha=16,              # scaling factor (usually 2 × r)
    target_modules=["c_attn"], # which layers to add LoRA to (GPT-2 specific)
    lora_dropout=0.05,
    bias="none"
)

# --- Step 4: Apply LoRA to model ---
lora_model = get_peft_model(model, lora_config)

# --- Step 5: Check parameters AFTER LoRA ---
lora_model.print_trainable_parameters()

# --- Step 6: See exactly which layers are trainable ---
print("\nTrainable layers:")
for name, param in lora_model.named_parameters():
    if param.requires_grad:
        print(f"  {name:60} shape: {list(param.shape)}")
```

---

### 6. Output Explanation

```
Before LoRA — Total parameters: 124,439,808

trainable params: 294,912
all params:       124,734,720
trainable%:       0.2365%

Trainable layers:
  base_model.model.transformer.h.0.attn.c_attn.lora_A.default.weight   shape: [8, 768]
```

**What this tells you:**
- Only **294,912** numbers are being trained instead of 124 million
- That is **0.24%** of the model
- Memory required drops dramatically
- Training is 10–50× faster

---

### 7. Common Mistakes

| Mistake | Reality | Fix |
|---------|---------|-----|
| Choosing r too low (r=1 or r=2) | Adapter has no capacity to learn anything useful | Start at r=8, increase if quality is poor |
| Applying LoRA to wrong layers | No improvement in output quality | Target attention layers: q_proj, v_proj (most impactful) |
| Forgetting to merge before deployment | Two separate things to manage in production | Call `merge_and_unload()` to merge adapters into base weights |
| Using LoRA when you need full fine-tune | LoRA may not fully capture complex domain shifts | If LoRA quality is consistently poor, consider full fine-tuning on a subset |

## Concept 3 — QLoRA (Quantized LoRA)

### 1. Real-World Problem (Hook)

LoRA reduced trainable parameters to 0.24% — great. But the base model still needs to be **loaded into GPU memory** to run the forward pass during training.

A Llama 3 70B model in full precision (fp32) = **280 GB** of memory. Even in fp16 = **140 GB**. You would need 2–4 high-end data centre GPUs just to load it.

**QLoRA solves this** — it compresses the base model to 4-bit (like shrinking a HD video to a tiny file), so the same 70B model fits in **~40 GB** — a single high-end GPU.

---

### 2. Simple Concept Explanation

**Quantization** = storing numbers in a lower-precision format to save memory.

Normal neural network weights are stored in **32-bit or 16-bit** floating point numbers.

QLoRA stores the base model weights in **4-bit** (called NF4 — NormalFloat4):

```
fp32: each weight takes 32 bits of memory
fp16: each weight takes 16 bits  (2× smaller)
int8: each weight takes  8 bits  (4× smaller)
nf4:  each weight takes  4 bits  (8× smaller)
```

Then LoRA adapters are kept in **fp16** (full precision) for training quality.

Result: the model fits in memory, the adapters train accurately, and you get full fine-tuning quality at a fraction of the cost.

---

### 3. Diagram

```
WITHOUT QLoRA:
┌──────────────────────────────────────────────┐
│  Base Model Weights  (70B × fp16 = 140 GB)  │  ← does not fit on 1 GPU
└──────────────────────────────────────────────┘

WITH QLoRA:
┌──────────────────────────────────────────────┐
│  Base Model Weights  (70B × nf4 =  35 GB)   │  ← compressed, frozen
└──────────────────────────────────────────────┘
              +
┌─────────────────────────────────┐
│  LoRA Adapters  (fp16, tiny)    │  ← trainable, full precision
└─────────────────────────────────┘

Total memory during training: ~40 GB  →  fits on 1× A100 GPU
```

---

### 4. Step-by-Step Breakdown

```
Step 1 → Load the base model in 4-bit precision (NF4 format)
         The model is compressed as it loads — weights lose some precision
         but performance stays high due to a clever normalisation trick

Step 2 → Freeze all compressed weights
         They cannot be updated during training
         (you cannot backpropagate through 4-bit integers directly)

Step 3 → Apply LoRA adapters in fp16
         Only adapters are trained — they stay in full precision

Step 4 → During forward pass:
         4-bit weights are temporarily dequantized to fp16 for computation
         Then compressed back — this happens layer by layer to save memory

Step 5 → Gradients flow only through the LoRA adapters
         Base model weights never change

Step 6 → Save only the LoRA adapter weights
         The base model stays as-is (available from HuggingFace)
```

---

### 5. Code Implementation

```python
# pip install transformers peft bitsandbytes accelerate

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, TaskType

# --- Step 1: Define 4-bit quantization config ---
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,                        # load base model in 4-bit
    bnb_4bit_quant_type="nf4",               # NormalFloat4 format
    bnb_4bit_compute_dtype=torch.float16,    # compute in fp16 during forward pass
    bnb_4bit_use_double_quant=True           # quantize the quantization constants too
)

# --- Step 2: Load model in 4-bit ---
# (use a real model name here if you have GPU access)
# model_name = "meta-llama/Llama-3.1-8B"
model_name = "gpt2"  # for local CPU demo (no 4-bit on CPU, shows config only)

tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token

# On a real GPU:
# model = AutoModelForCausalLM.from_pretrained(
#     model_name,
#     quantization_config=bnb_config,
#     device_map="auto"        # automatically place layers across GPUs
# )

# For CPU demo (no quantization):
model = AutoModelForCausalLM.from_pretrained(model_name)

# --- Step 3: Apply LoRA on top ---
lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,
    lora_alpha=32,
    target_modules=["c_attn"],
    lora_dropout=0.05,
    bias="none"
)

qlora_model = get_peft_model(model, lora_config)
qlora_model.print_trainable_parameters()

# --- Step 4: Memory comparison (conceptual) ---
def estimate_memory_gb(params: int, bits: int) -> float:
    return (params * bits) / (8 * 1024**3)

params_8b = 8_000_000_000

print(f"\nMemory estimates for 8B model:")
print(f"  fp32 (32-bit): {estimate_memory_gb(params_8b, 32):.1f} GB")
print(f"  fp16 (16-bit): {estimate_memory_gb(params_8b, 16):.1f} GB")
print(f"  int8 ( 8-bit): {estimate_memory_gb(params_8b,  8):.1f} GB")
print(f"  nf4  ( 4-bit): {estimate_memory_gb(params_8b,  4):.1f} GB")
```

```

all params:       124,734,720
trainable%:       0.4729%

Memory estimates for 8B model:
  fp32 (32-bit): 29.8 GB

  nf4  ( 4-bit):  3.7 GB   ← QLoRA loads the model here
```

---

### 7. Common Mistakes

| Mistake | Reality | Fix |
|---------|---------|-----|
| Using `load_in_8bit` thinking it is same as QLoRA | 8-bit is less compressed, uses more memory | Use `load_in_4bit` with `nf4` for full QLoRA benefit |
| Running 4-bit on CPU | `bitsandbytes` requires a CUDA GPU | Always use GPU for QLoRA training |
| Expecting same quality as full fine-tuning | 4-bit quantization introduces tiny precision loss | For most tasks, quality difference is negligible. Run evals to confirm |
| Not setting `device_map="auto"` | Model loads entirely on one GPU, may crash | Use `device_map="auto"` to spread across available GPUs |

## Concept 4 — RLHF vs DPO (Alignment Training)

### 1. Real-World Problem (Hook)

You have fine-tuned your model on legal documents. It now speaks like a lawyer.

But it has a new problem — sometimes it gives **confidently wrong answers**, uses **inappropriate tone**, or occasionally says something **harmful**.

You need to teach it **human preferences** — not just what is correct, but what humans actually prefer and find helpful, safe, and appropriate.

That is what alignment training does. Two main approaches: **RLHF** and **DPO**.

---

### 2. Simple Concept Explanation

**RLHF (Reinforcement Learning from Human Feedback):**
Humans compare two model outputs and pick the better one. A separate "reward model" learns to predict human preferences. The main model is then trained to maximise that reward score.

**DPO (Direct Preference Optimization):**
Skips the reward model entirely. Directly trains on the (preferred, rejected) pairs using a smarter mathematical trick. Simpler, faster, increasingly the industry standard.

**Analogy:**

| | RLHF | DPO |
|--|------|-----|
| Process | Hire a judge (reward model) → train to please the judge | Learn directly from human votes, no judge needed |
| Complexity | High — two training stages | Low — one training stage |
| Stability | Often unstable (RL is tricky) | Much more stable |

---

### 3. Diagram

```
RLHF PIPELINE:

Human Feedback
  "Response A is better than B"
        ↓
  Train Reward Model
  (learns to score responses like a human would)
        ↓
  Use PPO (RL algorithm)
  to train main model to maximise reward score
        ↓
  Aligned Model

─────────────────────────────────

DPO PIPELINE:

Human Feedback
  "Response A is better than B"
        ↓
  Directly train main model
  using (chosen, rejected) pairs as a loss function
        ↓
  Aligned Model  ← same result, fewer steps
```

---

### 4. Step-by-Step Breakdown

```
RLHF Steps:
Step 1 → Collect human preference data
         Show humans two responses to same prompt
         They pick which one is better

Step 2 → Train reward model
         Input: (prompt + response)
         Output: a score (how good is this response?)

Step 3 → Use PPO to fine-tune LLM
         LLM generates responses
         Reward model scores them
         PPO adjusts LLM weights to get higher scores
         (This is where instability can happen)

─────────────────────────────────

DPO Steps:
Step 1 → Collect human preference data
         Same as RLHF — chosen vs rejected pairs

Step 2 → Train LLM directly on pairs
         Loss function pushes model to:
         → increase probability of chosen response
         → decrease probability of rejected response

Step 3 → Done. No reward model. No RL.
```

---

### 5. Code Implementation

```python
# DPO training example using the TRL library
# pip install trl transformers peft

from trl import DPOTrainer, DPOConfig
from transformers import AutoModelForCausalLM, AutoTokenizer
from datasets import Dataset

# --- Step 1: Load model ---
model_name = "gpt2"
tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token

model = AutoModelForCausalLM.from_pretrained(model_name)
ref_model = AutoModelForCausalLM.from_pretrained(model_name)  # reference (frozen copy)

# --- Step 2: Prepare preference data ---
# Each example has: prompt, chosen response, rejected response
preference_data = [
    {
        "prompt": "What is the capital of France?",
        "chosen": "The capital of France is Paris.",
        "rejected": "France has many cities. I think it might be Lyon or maybe Paris, not sure."
    },
    {
        "prompt": "Explain photosynthesis simply.",
        "chosen": "Plants use sunlight to convert water and CO2 into food and oxygen.",
        "rejected": "Photosynthesis is a complex biochemical process involving chlorophyll molecules..."
    },
    {
        "prompt": "How do I improve my sleep?",
        "chosen": "Keep a consistent sleep schedule, avoid screens before bed, and keep your room cool and dark.",
        "rejected": "Sleep is very important. You should try to sleep more."
    }
]

dataset = Dataset.from_list(preference_data)

# --- Step 3: DPO training config ---
dpo_config = DPOConfig(
    output_dir="./dpo_model",
    num_train_epochs=3,
    per_device_train_batch_size=1,
    beta=0.1,          # controls how strongly to stay close to the reference model
    max_length=256,
    logging_steps=1,
    save_strategy="no"
)

# --- Step 4: Train ---
dpo_trainer = DPOTrainer(
    model=model,
    ref_model=ref_model,
    args=dpo_config,
    train_dataset=dataset,
    tokenizer=tokenizer
)

dpo_trainer.train()
print("DPO alignment training complete.")
```

---

### 6. Output Explanation

```
Step 1/3 - rewards/chosen: -2.34, rewards/rejected: -3.12
Step 2/3 - rewards/chosen: -1.87, rewards/rejected: -3.45
Step 3/3 - rewards/chosen: -1.52, rewards/rejected: -3.89
```

**What these numbers mean:**
- `rewards/chosen` should increase (model assigns higher probability to preferred responses)
- `rewards/rejected` should decrease (model assigns lower probability to bad responses)
- The gap between them growing = alignment is working

---

### 7. Common Mistakes

| Mistake | Reality | Fix |
|---------|---------|-----|
| Chosen and rejected responses too similar | Model cannot learn meaningful preference | Make chosen clearly better — not just slightly different wording |
| Too little preference data | Model barely aligns | Minimum ~1,000 preference pairs for noticeable improvement |
| Setting beta too low | Model drifts too far from its original behaviour | Keep beta between 0.05–0.5 |
| Skipping reference model in DPO | Training becomes unstable | Always provide a frozen reference model (copy of base before DPO) |

## Concept 5 — Decision Framework: What to Use When

### 1. Real-World Problem (Hook)

Your manager says: *"Our chatbot keeps giving wrong answers about our products. Fix it."*

You now have multiple tools available:
- Prompt engineering
- RAG
- Fine-tuning (SFT)
- LoRA / QLoRA
- DPO

Which one do you reach for first?

Getting this decision wrong wastes weeks of GPU time and money. Getting it right solves the problem in a day.

---

### 2. Simple Concept Explanation

Each technique solves a **different type of problem**:

| Problem Type | Right Tool |
|-------------|-----------|
| Wrong output format or style | Prompt engineering |
| Missing / outdated knowledge | RAG |
| Wrong behaviour, tone, domain expertise | Fine-tuning (SFT) |
| Fine-tuning but limited GPU | LoRA / QLoRA |
| Model is harmful or unhelpful in tone | DPO / RLHF |

---

### 3. Diagram — Decision Tree

```
Is the problem about OUTPUT FORMAT or TONE?
    ├── Yes → Try PROMPT ENGINEERING first (free, instant)
    │          Does it work?
    │              ├── Yes → Done
    │              └── No  → Move to fine-tuning
    │
    └── No  ↓

Is the problem about MISSING KNOWLEDGE
(company data, recent events, private documents)?
    ├── Yes → Does the knowledge change frequently?
    │              ├── Yes → RAG (update knowledge without retraining)
    │              └── No  → RAG or fine-tuning (either works)
    │
    └── No  ↓

Is the problem about WRONG BEHAVIOUR
(wrong reasoning style, unsafe outputs, bad tone)?
    ├── Yes → FINE-TUNING (SFT)
    │          Limited GPU budget?
    │              ├── Yes → LoRA / QLoRA
    │              └── No  → Full fine-tuning
    │
    └── No  ↓

Is the problem about ALIGNMENT
(model gives harmful, unhelpful, or biased outputs)?
    └── Yes → DPO or RLHF
```

---

### 4. Step-by-Step Breakdown

```
Step 1 → Diagnose the actual problem
         Ask: "Is the model wrong because it doesn't know, or because it behaves wrong?"
         Know    → RAG
         Behaves → Fine-tuning

Step 2 → Always try prompt engineering first
         It costs nothing and takes 10 minutes
         If it works, you saved weeks of work

Step 3 → If knowledge is the issue, implement RAG
         Faster than fine-tuning
         Knowledge stays up to date
         Citations are possible

Step 4 → If behaviour is the issue, fine-tune
         Decide: full fine-tune vs LoRA based on GPU budget
         Collect 1,000–10,000 instruction-response pairs

Step 5 → If alignment is the issue, use DPO
         Collect 500–5,000 preference pairs
         Train with DPO on top of your fine-tuned model

Step 6 → Combine as needed
         Best systems use: RAG (knowledge) + Fine-tuned (behaviour) + DPO (alignment)
```

### 5. Code — Decision Helper

```python
def recommend_approach(problem: dict) -> str:
    """
    Given a problem description, recommend the right fine-tuning approach.
    
    problem keys:
      - issue: "format" | "knowledge" | "behaviour" | "alignment"
      - knowledge_updates: True/False  (does knowledge change often?)
      - gpu_budget_gb: int             (available GPU memory in GB)
      - data_available: int            (number of labeled examples available)
    """
    issue = problem.get("issue")
    knowledge_updates = problem.get("knowledge_updates", False)
    gpu_gb = problem.get("gpu_budget_gb", 8)
    data = problem.get("data_available", 0)

    if issue == "format":
        return "Try PROMPT ENGINEERING first. If insufficient, use SFT with format examples."

    elif issue == "knowledge":
        if knowledge_updates:
            return "Use RAG — knowledge updates frequently, retraining would be too slow."
        elif data < 500:
            return "Use RAG — not enough data for fine-tuning."
        else:
            return "Use RAG for freshness, optionally add fine-tuning for domain style."

    elif issue == "behaviour":
        if data < 500:
            return "Not enough data for fine-tuning. Improve prompts or collect more data."
        elif gpu_gb >= 40:
            return "Full fine-tuning is possible with your GPU budget."
        elif gpu_gb >= 16:
            return "Use LoRA — good balance of quality and efficiency."
        else:
            return "Use QLoRA — 4-bit quantization required for your GPU size."

    elif issue == "alignment":
        return "Use DPO — collect preference pairs (chosen vs rejected) and align the model."

    return "Problem unclear — diagnose further."


# Test it
cases = [

    {"issue": "alignment", "knowledge_updates": False, "gpu_budget_gb": 40, "data_available": 800},
    {"issue": "format",   "knowledge_updates": False, "gpu_budget_gb": 8,  "data_available": 50},
]

for i, case in enumerate(cases, 1):
```

### 7. Common Mistakes

| Mistake | Reality |
|---------|---------|
| Jumping to fine-tuning as the first solution | Prompt engineering or RAG often solves it in a fraction of the time |
| Using RAG when the problem is behaviour | RAG adds knowledge, it does not change how the model reasons or responds |
| Fine-tuning for knowledge that changes | Your model becomes stale the moment the knowledge updates |
| Doing SFT + DPO on day 1 with no data | You need real examples and preference pairs — collect them first |

## Chapter Summary

| Concept | Core Idea | Key Terms |
|---------|-----------|-----------|
| Fine-Tuning (SFT) | Continue training on your domain data | Instruction format, epochs, loss, overfitting |
| LoRA | Train tiny adapter matrices, freeze base weights | Rank r, A×B matrices, 0.24% trainable |
| QLoRA | LoRA + 4-bit base model compression | NF4, bitsandbytes, device_map |
| RLHF | Align via reward model + RL (PPO) | Reward model, PPO, reward hacking |
| DPO | Align directly on chosen/rejected pairs | Beta, reference model, preference pairs |
| Decision Framework | Right tool for right problem | RAG=knowledge, SFT=behaviour, DPO=alignment |
